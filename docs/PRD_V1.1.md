# 1. 文档目的

本文档定义冰箱食材管理设备第一版（MVP）的产品目标、范围、用户流程、功能需求、业务规则、硬件约束与验收标准，作为微信小程序、服务端、ESP32 固件和电子墨水屏联调的共同基线。

> 核心结论：第一版先验证“低成本录入是否足够方便、到期信息是否真正帮助用户减少遗忘和浪费”。硬件保持纯展示，复杂操作全部放在微信小程序中完成。

# 2. 产品概述

## 2.1 产品定位

第一阶段为个人使用的 DIY 原型，完成端到端验证后开源。暂不以量产、商业销售和跨平台规模化运营为目标。

产品由四部分组成：

- 微信小程序：订单图片导入、语音辅助录入、库存管理、家庭共享与设备配置。
- 服务端：用户与家庭数据、图片识别任务、保鲜期计算、提醒调度和屏幕画面生成。
- 显示设备：ESP32-S3 N16R8、GDEM075F53 7.5 英寸 800×480 黑白黄红四色电子墨水屏、DESPI-C02 3.3V SPI 转接板、2.4 GHz Wi-Fi 与 USB-C 供电。
- 冰箱端入口：设备外壳上的小程序码，用于快速进入对应冰箱；NFC 暂不纳入第一版。

> 方案边界：硬件与固件设计参考“鲜知贴 / fridge_tracker”的 ESP32-S3、四色墨水屏、原生帧下载和外壳实现；本项目用户端仍采用微信小程序，不采用参考项目的 H5 页面作为产品入口，也不照搬其 Node.js、SQLite 或 SoftAP 网页配网方案。

## 2.2 用户问题

- 线上买菜订单商品较多，逐项手工录入成本高。
- 食材进入冰箱后容易被遗忘，用户无法快速判断应该先吃什么。
- 家庭成员共同使用冰箱，库存变化难以由一个人完整维护。
- 生鲜商品通常没有可直接使用的准确过期日期，只能给出合理的建议食用时间。

## 2.3 产品价值

- 用订单图片批量创建待入库清单，降低首次录入成本。
- 用手机输入法语音快速完成零散增删改查。
- 在冰箱门上持续展示“最应该先吃的食材”，无需打开手机查询。
- 通过家庭共享，让多人共同维护同一冰箱。

# 3. 产品目标与非目标

## 3.1 MVP 目标

1. 用户能够通过一张完整订单图片或多张截图批量识别商品，并在确认后入库。
2. 用户能够通过小程序完成食材新增、修改、消耗、丢弃和查询。
3. 系统能够按批次计算建议食用状态，并优先展示即将到期的食材。
4. 服务端数据变化后，电子墨水屏在目标时限内完成刷新。
5. 一个家庭空间可邀请多个成员共同管理，并保证设备数据隔离。
6. 用户可选择接收微信订阅提醒；未授权时不影响屏幕提醒和核心管理功能。

## 3.2 第一版非目标

- 不直接接入叮咚买菜、小象超市等平台的私有订单接口。
- 不承诺从订单图片获得生产日期或准确法定保质期。
- 不在冰箱内部安装摄像头做自动盘点。
- 不在硬件上增加麦克风、触摸屏、扫码枪或复杂实体按键。
- 不提供电池供电版本，不以超低功耗续航为首要指标。
- 不实现条形码扫描、包装日期识别和开封状态管理。
- 不实现官方 NFC 标签直接唤起小程序。
- 不实现多语言、营养分析、菜谱推荐和采购清单自动补货。

# 4. 目标用户与使用场景

## 4.1 目标用户

主要用户是经常通过线上买菜平台采购、希望减少食材浪费、愿意进行少量确认操作的年轻独居者、情侣或小家庭。

## 4.2 核心场景

### 场景 A：线上订单批量入库

用户从叮咚买菜保存完整订单分享图，或对小象超市订单分段截图。在小程序中一次选择一张或多张图片，系统识别商品并生成建议入库清单。用户确认冷藏、冷冻和常温分类后完成入库。

### 场景 B：零散食材快速录入

用户进入小程序的“快速记一笔”，通过手机输入法麦克风输入“今天买了两盒牛奶和一斤西红柿”。系统解析为结构化操作，展示确认结果后写入库存。

### 场景 C：食材消耗或丢弃

用户在清单中点击“吃完”或“丢弃”，也可以输入“牛奶喝完一盒”。存在多个批次时，系统默认优先扣减最早入库批次，并允许用户修改。

### 场景 D：冰箱门前查看提醒

用户无需拿出手机，即可在墨水屏上看到即将到期、今日建议食用和已超期的食材。屏幕最多展示 15 项，其余项目显示汇总数量。

### 场景 E：家庭共同维护

管理员邀请家庭成员加入同一家庭空间。成员能够共同增删食材，管理员负责设备绑定、成员管理和家庭设置。

# 6. 信息架构

小程序底部导航建议包含三个一级页面：

- 今日：到期摘要、快速记一笔、导入订单图片、重点食材。
- 食材：按冷藏、冷冻、常温查看全部食材，支持搜索和批量操作。
- 我的：家庭成员、设备、提醒设置、识别记录、隐私与开源信息。

主要二级页面：

- 订单图片选择页
- 识别中状态页
- 入库确认页
- 食材详情与批次页
- 家庭成员管理页
- 设备绑定与 Wi-Fi 配网页
- 提醒设置页
- 墨水屏相册页
- 水墨屏显示设置页（食材、黄历、相册三选一；食材和黄历显示对应预览，选择相册
  后提供相册管理入口）

# 7. 核心用户流程

## 7.1 订单图片入库

1. 用户点击“导入订单图片”。
2. 用户从相册选择一张完整分享图或多张截图。
3. 小程序展示上传进度并创建识别任务。
4. 服务端完成 OCR/视觉识别、商品结构化、跨图去重和非商品过滤。
5. 系统按冷藏、冷冻、常温和需要确认分组。
6. 用户调整商品、数量、入库日期、储存位置和建议食用天数。
7. 用户点击“确认入库”。
8. 服务端创建食材批次、更新屏幕版本并调度提醒。
9. 设备发现新版本后下载画面并刷新墨水屏。

## 7.2 快速记一笔

1. 用户进入“快速记一笔”文本框。
2. 用户打字或使用手机输入法自带的语音输入。
3. 服务端解析新增、消耗、丢弃、修改或查询意图。
4. 小程序展示结构化确认卡片。
5. 用户确认后执行；存在歧义时要求选择具体食材或批次。

## 7.3 食材到期提醒

1. 服务端每天重新计算食材状态。
2. 设备即使库存无变化，也至少每天刷新一次日期和剩余天数。
3. 用户开启微信提醒且当前存在可用订阅授权时，系统在设定时间发送汇总消息。
4. 用户从提醒进入小程序，可直接查看并处理对应食材。

## 7.4 墨水屏照片轮播

1. 家庭成员从“我的 → 水墨屏显示 → 独立相册 → 管理相册”选择一张 JPG/PNG。
2. 服务端修正方向、按中心裁切为 3:5、缩放为 480×800，并转换为黑、白、黄、
   红四色预览；原图不进入业务目录、数据库或对象存储，请求结束后释放临时文件。
3. 小程序展示最终四色效果，用户确认后照片才加入家庭轮播。
4. 家庭成员可以调整顺序、选择立即显示的照片，并设置 6、12 或 24 小时轮播周期。
5. 返回“水墨屏显示”选择独立相册后，设备下一次轮询取得全屏照片帧；此模式不显示食材、待办、
   小程序码或时间。
6. 用户在“水墨屏显示”选择食材管理，或删除最后一张确认照片后，设备恢复食材
   清单画面。

## 7.5 墨水屏黄历

1. 家庭成员进入“我的 → 水墨屏显示”。
2. 小程序从服务端取得按 `Asia/Shanghai` 计算的当日黄历并显示预览。
3. 用户选择“完整简版黄历”，服务端保存家庭级互斥显示模式。
4. 设备下一次轮询取得全屏四色黄历帧；同一天后续轮询返回 304。
5. 北京时间跨日后，版本号和 ETag 自动变化，设备刷新为新日期黄历。

# 8. 功能需求

## 8.1 微信登录与家庭空间

### FR-001 微信登录

- 使用微信小程序登录获取用户身份，不要求手机号作为核心功能前置条件。
- 首次登录时创建用户档案并展示隐私说明。

### FR-002 家庭空间

- 用户首次使用时可创建家庭空间并成为管理员。
- 管理员可以生成邀请入口，家庭成员确认后加入。
- 普通成员可查看、添加、修改、消耗和丢弃食材。
- 只有管理员可以解绑设备、移除成员和修改家庭级配置。
- 一个用户可以加入多个家庭，但第一版界面默认突出最近使用的家庭。

## 8.2 订单图片识别

### FR-010 图片选择与上传

- 支持从相册选择单张或多张图片，第一版目标一次至少支持 9 张。
- 支持常见 PNG、JPEG 和系统截图格式。
- 上传前可以压缩，但必须保持商品名称、规格和数量可辨识。
- 用户可取消未完成的上传或识别任务。

### FR-011 商品识别

- 输出字段至少包括商品名称、规格、数量、候选品类、建议储存位置和识别置信度。
- 过滤配送费、包装费、优惠券、订单编号、支付信息和营销文案。
- 对多张截图中的重叠商品进行去重，不得简单按同名全部合并。
- 无法可靠判断数量、规格或商品边界时，必须标记为“需要确认”。
- 识别失败时保留可重试入口，并允许用户跳过识别改为手工添加。

### FR-012 入库确认

- 默认选中建议进入冷藏或冷冻的食品。
- 常温商品默认不在冰箱屏幕展示，但用户可以选择纳入库存管理。
- 非食品默认不选中。
- 支持修改名称、数量、单位、入库日期、储存位置和建议食用天数。
- 用户明确确认后才写入正式库存，识别结果不得直接自动入库。

## 8.3 食材与批次管理

### FR-020 数据粒度

- 底层按批次保存，同一食材在不同入库日期下分别计算状态。
- 列表和屏幕可以聚合同名食材，但必须突出最早到期批次。
- 数量支持整数和小数，单位至少支持个、盒、袋、瓶、份、斤和克。

### FR-021 手工操作

- 支持新增、编辑、消耗、丢弃、恢复误操作和删除。
- “消耗”记录为正常使用；“丢弃”单独记录，便于后续统计浪费。
- 多批次扣减默认采用先到期先出库；执行前展示将被扣减的批次。

### FR-022 储存位置

- 第一版支持冷藏、冷冻和常温三个一级位置。
- 用户可以修改系统建议的位置。
- 墨水屏默认展示冷藏和冷冻，可在设置中选择是否包含常温。

## 8.4 快速记一笔与语音辅助

### FR-030 输入方式

- 第一版提供文本输入框，由用户选择键盘输入或手机输入法语音输入。
- 小程序不主动唤起系统听写，不在硬件上采集音频。

### FR-031 意图解析

- 支持新增、消耗、丢弃、修改数量、修改位置和查询。
- 模型输出必须转换为受约束的结构化操作，不允许直接生成数据库写操作。
- 所有写操作在执行前展示确认结果。
- 当目标不唯一时，必须要求用户选择，不得静默修改错误批次。

## 8.5 建议食用时间

### FR-040 规则来源

- 系统根据商品品类、储存位置和用户历史偏好给出建议食用天数。
- 第一版不区分开封与未开封状态。
- 用户可以修改本次批次的建议天数，并可选择保存为个人默认偏好。

### FR-041 表述边界

- 生鲜和缺少包装日期的商品统一使用“建议食用日期”或“建议尽快吃”。
- 不把模型估算值表述为法定保质期或食品安全保证。
- 包装食品若没有生产日期和有效期信息，同样按建议值处理。

## 8.6 状态与排序

| 状态 | 判定 | 展示规则 |
|---|---|---|
| 正常 | 剩余天数大于 3 天 | 黑色文字，按剩余天数升序 |
| 尽快吃 | 剩余 1～3 天 | 黄色强调，优先展示 |
| 今日建议食用 | 剩余 0 天 | 红色强调，置于尽快吃之前 |
| 已超期 | 剩余天数小于 0 | 红色强调，显示“已超期 N 天” |
| 无日期 | 无法计算建议日期 | 显示“待补充”，排在有日期项目之后 |

同一优先级下，按建议食用日期、入库日期和名称排序。

## 8.7 提醒

### FR-050 墨水屏提醒

- 屏幕持续显示库存状态，不依赖用户授权通知。
- 优先展示今日建议食用、已超期和尽快吃的食材。

### FR-051 微信订阅消息

- 用户可在小程序内主动申请微信订阅消息授权。
- 默认提醒时间为每天 20:00，用户可关闭或修改。
- 默认采用汇总提醒，不为每个食材分别发送消息。
- 系统仅在存在需要提醒的食材且有可用授权时发送。
- 个人主体可用模板、授权次数和发送限制以微信后台实际能力为准；没有可用模板时，MVP 仍视为可用。

## 8.8 设备绑定与配网

### FR-060 设备绑定

- 每台设备拥有唯一设备编号和设备密钥。
- 小程序码只携带公开设备编号或绑定入口，不携带长期登录凭证。
- 设备首次绑定需要管理员确认，并在服务端建立家庭与设备关系。

### FR-061 Wi-Fi 配网

- 第一版采用小程序蓝牙向 ESP32 传递家庭 Wi-Fi 信息。
- 配网过程中展示扫描、连接、凭据发送、联网验证和绑定结果。
- Wi-Fi 密码只用于设备配网，不写入业务日志，不向家庭普通成员展示。
- 配网失败时显示可理解的原因和重试入口。

## 8.9 屏幕内容与刷新

### FR-070 屏幕布局

- 使用 GDEM075F53 7.5 英寸 800×480 黑白黄红四色电子墨水屏。
- 产品按 480×800 竖屏方向安装和显示；服务端转换为面板 800×480 原生帧，
  ESP32 不重复旋转。
- 黑色显示普通内容，黄色显示“尽快吃”，红色显示“今日建议食用”和“已超期”；白色作为背景。若颜色转换发生冲突，红色优先于黄色，黄色优先于黑色。
- 顶部显示家庭/冰箱名称、当前日期和最近更新时间。
- 家庭管理员可在小程序配置冰箱名称，例如“小明的冰箱”；修改后，小程序和
  墨水屏使用同一个持久化名称。
- 主区域最多展示 15 项食材，优先级遵循状态排序规则。
- 单项至少显示食材名称、聚合数量和最紧急剩余天数。
- 超过 15 项时，底部显示“另有 N 项未显示”。
- 屏幕底部保留小程序码或设备入口标识。
- 中文字体、图标、排版和四色量化在服务端完成，ESP32 不承担字体排版，只负责下载、校验、缓存和刷屏。

### FR-071 刷新机制

- 服务端为每个设备维护画面版本号。
- USB-C 供电原型默认每 5 分钟检查一次新版本，间隔可配置。
- 设备使用 ETag 或等价版本标识发起条件请求；服务端返回 304 或版本未变化时，不下载帧且不刷新屏幕。
- GDEM075F53 原生四色帧目标长度固定为 96,000 字节；首次点屏必须按厂家 F53 示例确认字节内像素顺序和四色编码，确认后设备下载必须校验长度和完整性，再写入本地缓存并刷新。
- 库存变化后，目标是在 5 分钟内完成屏幕更新。
- 即使库存不变，设备也至少每天刷新一次日期和剩余天数。
- 下载、校验或刷新失败时保留上一帧，并在下一周期重试；不得用不完整帧覆盖有效缓存。
- 每次同步结束后关闭不需要的无线连接并让墨水屏进入休眠；USB-C 常供电版本可让 ESP32 在检查间隔内进入低功耗休眠。

## 8.10 独立相册模式

### FR-080 照片上传与确认

- 家庭管理员和普通成员都可以上传、查看、确认、删除和排序照片。
- 每个家庭最多保存 6 张，支持 JPG/PNG，单张不超过 5MB。
- 服务端修正 EXIF 方向，采用居中裁切生成 3:5 竖版画面，再缩放为 480×800。
- 照片使用黑、白、黄、红固定调色板和误差扩散抖动生成最终预览。
- 上传后必须由用户核对预览并确认；未确认照片不得出现在设备轮播中。
- 原始上传文件只用于当次处理，不写入业务目录、数据库或对象存储；请求结束后
  释放框架临时文件。
- 生产环境只保存处理后的 PNG，存储于私有腾讯云 COS；小程序必须通过后端家庭
  权限校验读取，不能直接获得公共 COS 地址。

### FR-081 显示模式与轮播

- 食材清单、完整简版黄历和独立相册是三个互斥显示模式。
- 独立相册模式使用完整 480×800 逻辑画布，只显示照片，不叠加食材、待办、
  小程序码、日期或更新时间。
- 轮播周期可选 1、3、6、12、24 小时，默认 6 小时；全部家庭成员都有修改权限。
- 用户可以选择一张已确认照片立即成为当前照片；设备在下一次联网轮询时刷新。
- 轮播顺序固定且可调整；到达周期边界后从下一张循环继续。
- 没有确认照片时不得开启相册模式。删除最后一张确认照片后自动恢复食材清单模式。
- 设备下载协议、HMAC 鉴权、96,000 字节帧长度和 ETag 条件刷新保持不变。

## 8.11 完整简版黄历模式

### FR-082 黄历计算与展示

- 服务端固定使用 `lunar-python 1.4.8`、默认 `sect=1` 和 `Asia/Shanghai` 日期，
  ESP32 不计算黄历、不保存黄历算法。
- 全屏显示公历年月日、星期、农历年月日、年月日干支、生肖、节气或节日、
  前 4 项“宜”、前 4 项“忌”以及“冲（干支）生肖 · 煞方”。
- 宜忌按算法返回顺序截取，不由系统重新排序；界面固定显示“传统民俗，仅供参考”。
- 家庭管理员和普通成员都能切换显示模式；无须重新烧录固件。
- 同一天、同一算法和排版版本生成稳定 ETag；北京时间跨日后才产生新黄历版本。

| 项目 | 第一版基线 | 要求与边界 |

第一版实物已确认采用“GDEM075F53 屏幕面板 + DESPI-C02 转接板”。屏幕批次或转接板变化后，必须重新核对 FPC、供电、逻辑电平、RESE 电阻档位和驱动兼容性。

## 11.2 ESP32-S3 与屏幕接线基线

| 屏幕转接板信号 | ESP32-S3 N16R8 | 说明 |
|---|---|---|
| GND | GND | 电源地共地 |
| 3V3 / VCC | 3V3 | 屏幕供电与信号逻辑统一使用 3.3V |
| SCK / CLK | GPIO12 | SPI 时钟 |
| SDA / DIN / MOSI | GPIO11 | SPI MOSI；此处 SDA 不是 I²C |
| RST / RES | GPIO7 | 屏幕复位 |
| DC | GPIO8 | 数据/命令选择 |
| CS1 / CS | GPIO10 | SPI 片选 |
| BUSY | GPIO9 | 屏幕忙状态输入 |
| CS2 | 不连接 | 第一版不使用 |
| MISO | 不连接 | 屏幕帧仅需单向写入 |

接线和拆线必须在断电状态下完成。FPC 不得反插或带电插拔。ESP32 天线区域应远离屏幕排线、磁铁和大面积金属；如出现 Wi-Fi 信号明显下降，应优先检查供电压降、USB 3.x 干扰、天线遮挡和连接线质量。

## 11.3 固件与原生帧约束

- 固件面板类型必须锁定为 GDEM075F53/JD79665CA，对应 800×480 四色驱动。
- 首次点屏以 Good Display 发布的 GDEM075F53 ESP32 示例为驱动基线；不得直接沿用 GDEM075F52/JD79665AA 的初始化序列或字节编码假设。
- DESPI-C02 的 RESE 开关必须在断电状态下设为 2.2Ω，确认档位后才能插入屏幕 FPC 并上电。
- 服务端负责中文排版、图标绘制和黑/白/黄/红颜色量化，并输出 96,000 字节原生四色帧。
- ESP32-S3 使用 PSRAM 缓存完整帧；设备不得在 RAM 中重新排版中文页面。
- 设备本地保存最近一次有效帧及其 ETag/版本号。服务端返回 304 时不重复刷新。
- 下载完成后必须校验 HTTP 状态、内容长度和帧校验值；只有完整有效的新帧才允许覆盖缓存。
- 刷屏完成后屏幕进入休眠；ESP32 在下一次检查前可进入低功耗休眠，唤醒后重新连接 Wi-Fi。
- 固件必须通过编译期面板配置或设备型号阻止错误驱动刷写到不匹配的屏幕。

## 11.4 配网、复位与设备绑定

- 正式用户路径保持“微信小程序 BLE 配网”，不得要求用户打开 H5 或浏览器配置页面。
- 首次绑定由小程序识别设备编号，完成安全握手后传递 2.4 GHz Wi-Fi 配置和一次性绑定凭据。
- 长按配网键 5 秒进入重新配网模式；清除 Wi-Fi 配置前必须保留设备编号，不得生成重复设备记录。
- 配网凭据、Wi-Fi 密码和设备长期令牌不得通过串口或业务日志明文输出。
- 开发阶段可以使用串口写入测试网络，但该入口不得进入最终用户说明。

## 11.5 外壳与参考实现边界

- 外壳设计可参考 fridge_tracker 提供的 7 英寸级 3D 打印结构，但不得直接假设其 7.2 英寸外壳尺寸适配 GDEM075F53。
- 打印前使用卡尺复测屏幕外形、可视区、FPC 弯折空间、转接板高度、USB-C 插拔空间、按键行程和磁铁位置。
- 前框不得压迫屏幕有效显示区或 FPC；后壳应允许拆卸维护，并为 ESP32 天线保留非金属净空区。

# 12. 非功能需求

## 12.1 性能

- 单次图片导入任务在正常网络下目标 30 秒内返回首个可确认结果；超时应显示持续处理中而非失败假象。
- 常用库存列表首屏目标 2 秒内可用。
- 库存更新到屏幕完成刷新的目标时间不超过 5 分钟。

## 12.2 可靠性

- 识别、库存写入和画面生成采用任务状态或幂等标识，避免重试造成重复入库。
- 设备离线不影响小程序管理，恢复联网后拉取最新完整画面。
- 屏幕刷新失败不得清空已有画面。
- 条件请求返回 304 时不得触发重复刷屏；帧长度或校验失败时不得覆盖最近有效缓存。

## 12.3 安全与隐私

- 订单图片可能包含姓名、电话和地址，上传前明确说明用途。
- 原始图片识别后删除，最长保留不超过 24 小时；日志不得记录图片内容和 Wi-Fi 密码。
- 相册原图只在内存中用于裁切和四色转换，不长期保存；处理图使用私有对象存储，
  所有上传、预览、删除和设置接口必须校验家庭成员关系。
- 设备密钥、微信密钥和模型服务密钥不得提交到开源仓库。
- 所有服务端接口通过 HTTPS，库存操作必须进行用户、家庭和设备权限校验。
- 提供家庭退出、成员移除和个人数据删除入口。

## 12.4 可维护与开源

- 小程序、服务端、固件和屏幕渲染模块保持边界清晰。
- 提供环境变量示例、数据库迁移、部署说明、模拟设备和示例数据。
- 对 OCR/模型服务设计适配层，避免代码绑定单一供应商。
- 开源前完成许可证选择、第三方依赖清单和敏感信息扫描。
- 引用或复用 fridge_tracker 的固件、文档与 CAD 前单独核对 PolyForm Noncommercial 1.0.0，不将其误标为可自由商用的开源资产。

## 12.5 可用性

- 关键写操作必须有明确确认和成功反馈。
- 识别置信度低时优先让用户确认，不以减少点击为由隐藏风险。
- 状态颜色之外同时使用文字，避免只依赖黑、黄、红颜色传达信息。

# 16. 风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| 多张截图识别重复或漏项 | 库存不可信 | 利用版面位置、名称、规格和数量综合去重；低置信度强制确认 |
| 家庭成员忘记记录出库 | 形成幽灵库存 | 提供一键吃完、语音快速扣减和定期盘点提示 |
| 建议食用时间不准确 | 用户误解为安全承诺 | 统一使用“建议”措辞，允许修改并显示规则来源 |
| 微信订阅授权不可持续 | 无法稳定每日推送 | 把墨水屏作为主提醒渠道，微信消息仅为可选增强 |
| 个人主体限制硬件能力 | NFC 等官方能力不可用 | MVP 使用小程序码；后续迁移非个人主体再申请硬件接入 |
| 墨水屏刷新慢或失败 | 用户认为数据未同步 | 展示更新时间，保留上一帧，自动重试并在小程序显示设备状态 |
| 面板或转接板型号/档位错误 | 无法驱动、颜色异常或损坏硬件 | 锁定 GDEM075F53、DESPI-C02、3.3V SPI 与 RESE=2.2Ω；接线前核对型号、FPC 和电气参数 |
| 天线被屏幕、磁铁或冰箱金属遮挡 | Wi-Fi 配网困难或同步失败 | 外壳为天线预留非金属净空区，裸机阶段验证不同安装位置的信号质量 |
| 参考项目许可证限制 | 后续开源或商业化存在合规风险 | 只借鉴硬件思路；复制代码、CAD 或模型前完成 PolyForm Noncommercial 1.0.0 许可证审查 |
| 开源部署门槛过高 | 难以复刻 | 提供 Docker/一键脚本、模拟设备、可替换模型适配层和分阶段教程 |

# 17. 已确认决策与待验证项

## 17.1 已确认决策

- 第一阶段为个人 DIY 原型，完成后准备开源。
- 管理冷藏、冷冻和常温，屏幕默认重点展示冷藏与冷冻。
- 底层按批次记录，屏幕和列表允许聚合展示。
- 硬件仅展示，所有管理操作在微信小程序完成。
- 同时提供墨水屏提醒和可选微信订阅消息。
- 用户可修改建议食用天数，第一版不区分开封状态。
- 采用家庭空间，管理员负责成员与设备管理。
- 硬件基线采用 ESP32-S3 N16R8、GDEM075F53 7.5 英寸 800×480 黑白黄红四色墨水屏、DESPI-C02 3.3V SPI、USB-C 常供电和磁吸固定。
- 屏幕原生四色帧由服务端生成，固定为 96,000 字节；ESP32 只负责安全配网、版本检查、下载校验、缓存和刷屏。
- 参考 fridge_tracker 的硬件与固件思路，但用户端继续使用微信小程序，不采用其 H5 作为正式产品入口。
- 订单输入统一为“订单图片导入”，兼容完整分享图和多张截图。
- 第一版通过输入法语音输入，不做硬件麦克风和小程序录音识别。
- 当前小程序为个人主体，MVP 使用小程序码，暂不启用官方 NFC 唤起能力。
- 墨水屏增加独立全屏相册模式；最多 6 张，全部家庭成员可管理，轮播周期为
  6、12 或 24 小时，原图不保存，生产处理图存入私有腾讯云 COS。
- 墨水屏增加完整简版黄历模式；服务端以固定 `lunar-python 1.4.8` 计算，全部
  家庭成员可切换，按北京时间每日更新并保留民俗参考提示。

## 17.2 开发阶段待验证

- 叮咚买菜与小象超市不同版本订单图片的版式覆盖率。
- 微信个人主体后台可申请的食材提醒模板及实际订阅次数限制。
- GDEM075F53 实际采购批次的全刷时间、快速刷新能力、四色效果、原生帧编码和低温环境表现。
- BLE 配网在主流 iOS、Android 设备上的兼容性。
- 建议食用规则库的初始品类范围与数据来源。
- 屏幕 15 项容量在实际字号和二维码尺寸下的可读性。
- ESP32 天线在冰箱金属表面、磁铁和最终外壳共同影响下的信号强度。
