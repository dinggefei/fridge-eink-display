# 快速记一笔与订单图片识别设计

## 安全边界

- 模型只能产生受约束的草稿，不能直接访问数据库或调用库存接口。
- 所有写操作都必须由用户确认。
- 确认时锁定识别任务和家庭库存版本，避免识别后库存变化造成误扣。
- `X-Idempotency-Key` 与任务最终状态共同避免重复入库。
- 原始图片不写入数据库和日志；成功后立即删除，异常文件最长保留 24 小时。

## 快速记一笔

当前支持 `add`、`consume`、`discard`、`edit`，以及按食材名称、储存位置、
临期、今日到期和过期条件查询。服务端向文本模型提供当前家庭的候选库存，模型
返回名称、数量、单位和候选批次，后端再次验证批次确实属于当前家庭。

- 新增、消耗、丢弃和修改都必须先展示确认卡片。
- 修改范围限定为数量、单位、储存位置、入库日期和建议食用日期。
- 消耗和丢弃确认后按 FEFO（最早建议食用日期优先）扣减并记录
  `InventoryEvent`。
- 查询结果由后端根据数据库重新计算，不执行写操作，也不增加库存版本。
- 新增食材的建议日期按“准确食材名称 + 储存位置”匹配家庭规则；未匹配时使用
  冷藏 3 天、冷冻 30 天、常温 7 天的系统默认值。

## 订单图片

小程序先创建任务，再逐张上传最多 9 张图片。服务端验证图片、去除 EXIF、限制
像素和大小并转为 JPEG。生产 worker 默认最多并发调用 2 个视觉识别请求，过滤
非商品信息，并对相邻截图中名称、规格、数量和单位完全相同的重叠行去重。
低置信度商品保留在确认页，不会静默丢弃。

## 历史与指标

- 普通成员只能读取自己的识别历史和个人指标。
- 家庭管理员可读取家庭汇总指标，但历史列表仍只返回管理员自己的原始输入。
- 汇总记录任务来源、状态、图片数、识别/确认/纠正数量、平均置信度和耗时。
- 订单原图识别完成后仍立即删除，历史和指标接口不返回图片内容或路径。

## 运行方式

- 本地：`mock + inline`，可验证完整业务流程且不产生模型费用。
- 生产：`hunyuan + worker`，API 只负责上传和查询，独立 worker 调用模型。

模型层只依赖 OpenAI 兼容的 HTTP 形状，后续更换供应商时不改变业务接口和
数据库事务。
